## M1 review findings

1. **Critical — reports can disappear before a bot reads them.** If `buildContext` follows the current `orgContext()` behavior, it marks reports read while building the prompt. A missing CLI, cancellation, or startup failure then leaves the reports read with no successful bot turn. The new 3,000-character per-turn cap also requires care: a report cut off by that cap must remain unread. **Where:** [coordinator.mjs, `orgContext()`](runtime/coordinator.mjs:1226), [org.mjs, `markRead()`](runtime/org.mjs:90), plan §3.1. **Smallest fix:** return the IDs of reports included *in full* and mark only those IDs read when the run succeeds.

2. **High — M1 has no resumable session to receive delta prompts.** Every current run starts a new CLI process and receives one prompt on stdin. If M1 omits instructions, rules, or earlier messages because it considers a run a later “session turn,” the bot starts fresh without them. **Where:** [adapters.mjs, `runHarness()`](runtime/adapters.mjs:670), plan §§3.1, 3.2 and M1/M2. **Smallest fix:** keep every M1 run in fresh mode; enable delta prompts only alongside M2’s verified resume path.

3. **High — the action-guide gate removes instructions for usable actions.** In an empty project, “conversation has a board” can be read as false just when a bot needs `task.create`. The guide also describes `memory.save`, `report`, and `kg.fact`; those actions are not conditional on an existing board card. Today the CLI tools are output blocks, while Claude’s current Any Bot MCP config supplies an **approval** tool, not those action tools. A bot may finish prose successfully while its intended board or report update never happens. **Where:** [actions.mjs, `ACTION_GUIDE`](runtime/actions.mjs:47), [coordinator.mjs, `applyAction()`](runtime/coordinator.mjs:900), plan §3.1 layer 4. **Smallest fix:** gate each instruction on the specific available Any Bot action tools; until those exist, send the block guide wherever its actions are permitted.

4. **High — the “referenced report arrives whole” test conflicts with the clipping rule.** Suppose a teammate posts a 6,000-character analysis, this bot takes a turn, and the owner later asks it to revisit a detail in that analysis. The analysis is now older than the bot’s last turn, so §3.1 cuts it to its first and last 800 characters. M4’s `thread_read` is unavailable, and asking the teammate may not recover the text. **Where:** plan §3.1 history hygiene and M1 regression test; current history selection is in [coordinator.mjs, `promptParts()`](runtime/coordinator.mjs:1131). **Smallest fix:** exempt explicitly referenced message IDs from clipping, or provide a working read path before clipping them.

5. **High — name-only @mentions can run the wrong bot.** The employee editor permits two bots with the same name. In a project containing both, `@Alex` resolves to the first match; the second cannot be addressed reliably. A quoted `@Alex` in bot output can also activate a run because activation scans the entire visible reply. **Where:** [coordinator.mjs, `createEmployee()`](runtime/coordinator.mjs:457), [mentions.mjs, `mentionedIds()`](runtime/mentions.mjs:10), [coordinator.mjs, `activateMentions()`](runtime/coordinator.mjs:1681), plan §3.1 handoffs. **Smallest fix:** require unique case-folded names within a project or add an unambiguous mention identifier, and restrict activation to intentional mentions rather than quoted or fenced text.

6. **Medium — the 12,000-character history budget is incompatible with its exemptions.** A fresh run can have multiple 24,000-character messages since the bot’s last turn. §3.1 says none may be shortened, yet caps fresh history at 12,000 characters. An implementation must either fail its budget test or silently drop promised context. **Where:** plan §3.1 layer 5 and “Never clipped”; the current send limit is [coordinator.mjs, `send()`](runtime/coordinator.mjs:1005). **Smallest fix:** define the 12,000-character limit as applying only to *optional older* history, and test/report overflow from mandatory messages separately.

7. **Medium — the project-only team layer contradicts direct-chat delegation.** A manager in a one-bot direct chat can currently delegate to a report outside the conversation. Layer 3 says “projects only,” while the handoff paragraph and M1 test require the `anybot` block in that direct chat. Applying the layer gate literally silently removes the manager’s only delegation instruction. **Where:** plan §3.1 layer 3 and handoffs; [coordinator.mjs, `delegate()`](runtime/coordinator.mjs:1639). **Smallest fix:** give direct-report delegation its own condition, independent of project membership.

8. **Medium — the platform cap can cut operational paths.** Workspace paths can be long, and `allowedFolders` accepts up to ten paths without a character limit. A hard 900-character cap on a layer containing those paths, approval rules, and the artifact contract can omit an allowed folder or part of the artifact instructions; refusing the overflow instead can fail an otherwise valid run. **Where:** plan §3.1 layer 2; [coordinator.mjs, `validateProjectFolders()`](runtime/coordinator.mjs:638) and [`promptParts()`](runtime/coordinator.mjs:1192). **Smallest fix:** budget fixed rule text separately from variable paths and attachment metadata, and never truncate a path or required contract.

**What holds up:** Keeping the assignment as a separate, uncut final layer matches the current run model, where each run has a specific assignment message.

**First three changes:** keep M1 entirely in fresh mode; make report read status a post-success commit for fully included reports; replace the board/MCP guide gate with checks for the specific actions the harness can perform.
