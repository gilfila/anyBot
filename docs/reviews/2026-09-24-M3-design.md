## Findings (raw)

## M3 review

1. **Critical — a crash can lose the reply’s partial text.** A bot streams several paragraphs, the five second checkpoint has not run, and the worker crashes. Startup marks the run `interrupted`, but its SQLite `output` still contains the previous checkpoint. The terminal log cannot fill the gap reliably: it records formatted CLI events and tool activity, stops at 4 MB, and write errors are ignored. See [coordinator.mjs](runtime/coordinator.mjs:1353), [terminal.mjs](runtime/terminal.mjs:29), and M3 §3.3. **Smallest fix:** persist a separate append-only reply stream and replay it on startup, or retain the current SQLite write cadence until crash recovery is proven.

2. **High — `run.output` cannot safely be derived by appending each callback value.** `runHarness` calls `onText` with the *entire output so far*, while its final result may come from a distinct `final` event. Turning callbacks directly into append deltas duplicates text; assuming the streamed text equals the final reply can leave the live bubble different from the posted message. See [adapters.mjs](runtime/adapters.mjs:710) and [coordinator.mjs](runtime/coordinator.mjs:1455). **Smallest fix:** track the last emitted prefix per run, emit only its suffix, and send an explicit final reconciliation from the actual result.

3. **High — the 64 KB snapshot gate is impossible with the specified window.** On the committed 5,000-message corpus, the newest 100 messages alone serialize to **176,211 bytes**. The corpus also has 4,000 runs within seven days; even a stripped four-field representation takes **422,894 bytes**. See [corpus.mjs](scripts/corpus.mjs:169) and [M3 gate](docs/plans/lean-runtime.md:437). **Smallest fix:** make the budget apply to a compact initial summary response, and fetch message bodies and runs separately; then measure that exact response.

4. **High — replacing all mutation replies with `{epoch, seq}` breaks existing callers.** After `messages.send`, the renderer reads `result.messages` and `result.runs` to open the new thread. After `conversations.create`, it reads `next.conversations.at(-1)`. The mobile gateway does the same when creating a conversation. These paths throw or open the wrong item with the proposed reply. See [App.jsx](src/App.jsx:435) and [mobile-gateway.mjs](runtime/mobile-gateway.mjs:374). **Smallest fix:** return `{epoch, seq, result}` with stable created IDs, and migrate each caller to those IDs.

5. **High — the worker has no way to know which conversation is open.** The proposed snapshot gives one conversation 100 messages and others 20, but the current `snapshot` request carries no view selection; opening a conversation only changes React state. A newly opened conversation can therefore remain on its 20-message window. See [App.jsx](src/App.jsx:392), [coordinator.mjs](runtime/coordinator.mjs:219), and M3 §3.3. **Smallest fix:** pass the open conversation ID with each snapshot or issue a scoped page request when the selection changes.

6. **High — a late snapshot can erase a newer delta.** During startup or gap recovery, a snapshot at sequence 10 can be requested, sequence 11 can arrive and be applied, and then the sequence 10 reply can replace the store. The design specifies gap handling but no rule for this ordering; the current renderer replaces its state on every snapshot. See [App.jsx](src/App.jsx:337) and [M3 §3.3](docs/plans/lean-runtime.md:210). **Smallest fix:** install snapshots only if their epoch and sequence are at least as current as the store, buffering and replaying newer deltas during resync.

7. **High — command-only delta tests miss background changes.** Runs start in `dispatch`, stream and finish in `execute`, and routines tick on a timer; shell-owned updater and diagnostics state also changes outside coordinator commands. A table over commands can pass while live runs, approvals, or badges stay stale. See [coordinator.mjs](runtime/coordinator.mjs:173), [coordinator.mjs](runtime/coordinator.mjs:1311), and [main.cjs](desktop/main.cjs:593). **Smallest fix:** emit changes at the committed mutation boundary, including timer and run callbacks, and define a separate event path for shell state. Test those paths as well as commands.

8. **High — the window can contain no channel roots.** In the corpus, each thread contains 20 messages. The newest 100 messages can be replies belonging to only five threads, while their root messages are older than the window. The current channel and thread buttons are built from loaded root messages, so those threads have no visible entry point even if `threads.get` could open them by ID. See [App.jsx](src/App.jsx:383) and [threads.js](src/components/chat/threads.js:6). **Smallest fix:** page channel roots independently of replies and attach server summaries to those roots.

9. **Medium — the two kilobyte tick limit needs a completion rule.** If a CLI emits a 24 KB response immediately before exit, splitting it into 2 KB ticks leaves eleven ticks queued when the run completes. Removing finished-run output before those ticks drain loses visible text; sending them all at completion violates the gate. See [M3 exit gate](docs/plans/lean-runtime.md:423) and [coordinator.mjs](runtime/coordinator.mjs:1435). **Smallest fix:** drain ordered chunks before the completion event, or make completion replace the live bubble with the posted reply.

The CLI invocation and prompt construction paths do not need to change for M3; the main risks are state ordering, bounded responses, and durable output.

**First three changes:** define atomic snapshot/delta ordering; redesign the initial response to meet a measurable 64 KB budget; add a durable reply stream with final-result reconciliation.

## Triage

Every finding gets a verdict. High and critical findings are fixed, or rejected with evidence, before merge.

| # | Finding | Severity | Verdict | Evidence |
|---|---|---|---|---|
| 1 | A crash loses streamed text between 5 s checkpoints; the terminal log can't rebuild it | critical | Accepted | UI pushes and SQLite writes are decoupled: `runs.output` keeps a durable checkpoint at most 1 s apart (not 5 s) until an append-only reply stream with startup replay exists and is tested. Crash test in step 3. |
| 2 | `onText` passes the whole output so far; appends would duplicate; the final reply can differ | high | Accepted | The coordinator tracks the last emitted length per run and emits only the suffix; completion sends the posted reply, which replaces the live bubble. |
| 3 | The 64 KB snapshot gate is impossible with 100 messages + 7 days of runs (176 KB and 423 KB on the corpus) | high | Accepted | The initial response becomes a summary (conversations with unread counts and thread summaries, employees, active runs without output, the open conversation's newest 30 channel roots with summaries); bodies and older runs come by page. The 64 KB gate applies to that exact response, measured on the corpus before the gate is fixed. |
| 4 | `{epoch, seq}` replies break callers that read the new snapshot | high | Accepted | Mutations return `{epoch, seq, result}` with the created ids (`messageId`, `conversationId`, `runIds`); `App.jsx` and the mobile gateway move to those ids in step 1, while snapshots still exist. |
| 5 | The worker can't know which conversation is open | high | Accepted | `snapshot {open}` and `messages.page` when the selection changes. |
| 6 | A late snapshot can overwrite newer deltas | high | Accepted | The store installs a snapshot only if its (epoch, seq) is at least its own; deltas that arrive during a resync are buffered and replayed on top. Reducer tests. |
| 7 | A command-only test table misses changes from dispatch, streaming, timers, and shell state | high | Accepted | Changes are emitted at every committed mutation boundary (commands, `dispatch`, `execute`, routines, approvals). The main test is replay equivalence: after each scenario, the store built from deltas equals a fresh snapshot, whatever produced the change. Shell state (update, tray) keeps its own push. |
| 8 | The window can hold replies whose thread roots are outside it | high | Accepted | Channel roots are paged on their own with server thread summaries; replies load per open thread (`threads.get`). |
| 9 | 2 KB ticks need a completion rule | medium | Accepted | Pending chunks drain before the completion change; completion replaces the live bubble with the posted reply. |
